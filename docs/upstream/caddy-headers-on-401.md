# Upstream: security headers and `Server` are not applied to `basic_auth` rejections

**Status:** reproduced on Caddy 2.11.9, not filed yet. Paste the body below into a
new issue at <https://github.com/caddyserver/caddy/issues/new> after a search,
since nothing matching was found with `gh search issues --repo caddyserver/caddy
"deferred header 401"` on 2026-11-22.

**Suggested title:** `header` directive (deferred) is skipped on `basic_auth` 401 responses

---

### 1. What happens

With `basic_auth` and a `header` block in the same site, the headers are applied
to normal responses but **not** to the `401` that `basic_auth` produces. The
`Server: Caddy` header is also *not* removed on those responses, even with an
explicit `-Server`, so `-Server` silently fails on exactly the responses an
unauthenticated client receives.

### 2. Minimal reproduction

```caddyfile
{
	admin off
}

localhost {
	tls internal
	header {
		-Server
		X-Test "yes"
	}
	basic_auth {
		user $2a$14$bg6nNBpzLnTwPuNCluCBseSNJbsO6uG.dVQq7kl5Mke2iKNzV4a/W   # "secret"
	}
	respond "ok"
}
```

`caddy adapt` orders the handlers as expected — headers first, then auth:

```
server srv0 [':443']
    - subroute
        - headers (deferred)
        - authentication
        - static_response
```

Responses (`curl -k --resolve localhost:9443:127.0.0.1`):

```
# authorized
HTTP/2 200
x-test: yes                      ← set
# (no server: header)           ← removed

# unauthenticated
HTTP/2 401
server: Caddy                    ← NOT removed
www-authenticate: Basic realm="restricted"
content-length: 0
                                 ← x-test missing entirely
```

Same for wrong credentials. The behaviour is independent of the auth method's
outcome and of `hash_cache`; it is the rejection path.

### 3. Why it matters

`401` is the only response an unauthenticated attacker ever sees, so this is
where header hardening is worth the most and where it currently applies least:

* `-Server` is a documented hardening step; users reasonably assume it hides the
  product, but the banner survives on the rejection path (fingerprinting for
  version-specific exploits).
* Every other security header (`X-Content-Type-Options`, `X-Frame-Options`,
  `Content-Security-Policy`, `Referrer-Policy`, `Strict-Transport-Security`, …)
  is missing on `401`. With HSTS specifically, a visitor who only ever gets a
  `401` never receives the policy, so the first downgrade opportunity on any
  later request is unprotected.
* It also makes the deployment story confusing: the headers are provably
  configured (they show up on `200`), so the missing ones look like a
  misconfiguration on the user's side.

### 4. Guess at the cause (for triage, not a fix)

`headers` is a deferred handler: it wraps the `ResponseWriter` and applies its
changes on the way out. `basic_auth` writes its `401` without passing through the
wrapped writer — plausibly it writes directly to the original writer (or the
error path does), so the deferred wrapper never sees the response.

### 5. Expected behaviour

Either the deferred header handler applies to short-circuited responses
(consistent with the adapted handler order and with what users configure), or
the documentation for `header` states that responses generated by
authentication providers bypass it — either way, `-Server` should not be
advertised as working when it does not.

---

## What this repository does meanwhile

* Treats the headers as protection for **served** content only; the README says so
  explicitly under "Security".
* Keeps a smoke-test assertion that can only run with credentials
  (`--password`), because that is the only response that can show the headers.
* Uses fail2ban / rate limiting for the rejection path, since headers cannot
  help there (they would not stop brute force anyway).
